Core gameplay

Win by leaving the opponent with no legal move. Plus retains four pieces per player but adds a second vacancy, so choosing which space to leave open becomes part of the strategy.

Core game design

A small rule change had consequences across the game: some pieces gained multiple destinations, the interface had to ask the player to choose, and the AI had more branches to evaluate.

Inside the implementation

Three difficulties, one rule model

The three opponents differ in how they choose, while sharing Board’s legal moves and victory conditions. Easy samples a legal move at random. Medium and Hard use the same adversarial search with different planning horizons, so their strength comes from considering more replies.

01 / Difficulty changes the planning horizon

Search depth counts individual moves by either player, rather than complete rounds. Medium examines a candidate move and up to four alternating replies; Hard extends that horizon to thirteen moves. A terminal result ends a branch earlier. These limits are configuration values in Difficulty.java.

02 / Search from both players’ perspectives

For each legal action, the AI copies the position, applies the move and searches the opponent’s strongest continuation. Negamax scores every position for the side whose turn it is. Negating a reply score converts it back to the previous player’s perspective: a reply worth +24 to the opponent is worth −24 to the computer.

The highest score selects the move. Equal scores retain the first generated action, making Medium and Hard reproducible for a fixed board. Easy deliberately keeps its random choice. Each Plus source-and-destination pair is a separate branch, so choosing which vacancy to occupy is part of the search.

03 / Evaluate mobility, recognise a forced result

At the depth limit, mobility estimates how much freedom each player has. Three legal moves against one score 8 × (3 − 1) = +16 for the side to move. This encourages keeping options open; a trap beyond the horizon can still be missed. A known win or loss outweighs this estimate because WIN is 10,000. The remaining-depth term favours earlier wins and postpones unavoidable losses.

Annotated source excerpt: AIPlayer.java · search().

private int search(Board position, int depth) {
    // Allow a cancelled worker search to stop between branches.
    if (Thread.currentThread().isInterrupted()) return 0;
    // A blocked side loses. More remaining depth means an earlier loss.
    if (position.checkWinner() != null) return -WIN - depth;
    if (position.isDraw()) return 0;
    if (depth == 0) {
        Board.Piece turn = position.getCurrentPlayer();
        // Estimate freedom to move from the current side's perspective.
        return position.legalMoves(turn).size() * 8 -
            position.legalMoves(Board.opponent(turn)).size() * 8;
    }

    // Layout, side to move, move count and horizon define this result.
    String key = position.stateKey() + ":" +
                 position.getMoveCount() + ":" + depth;
    Integer cached = memo.get(key);
    if (cached != null) return cached;

    int best = Integer.MIN_VALUE;
    for (Board.Move move : position.legalMoves(position.getCurrentPlayer())) {
        // Explore a private branch without changing the live match.
        Board next = position.copy();
        next.applyMove(move.from(), move.to(), position.getCurrentPlayer());
        // The reply is scored for the opponent; negate it for this side.
        best = Math.max(best, -search(next, depth - 1));
    }
    // Reuse only a fully evaluated result under the same search conditions.
    memo.put(key, best);
    return best;
}

04 / Reuse work and keep the interface responsive

Different move sequences can reach the same position. A hash map caches completed results using the layout, side to move, elapsed move count and remaining depth. Including the horizon prevents a shallow evaluation from being reused as a deeper result; the cache is cleared before each decision.

The search runs on a copied board in a worker thread. Its selected action returns to the JavaFX thread with a match revision token. A result from an earlier match is discarded after a restart, so a long Hard search cannot alter the new board.

A closer look

Let the AI think without freezing the board.

The challenge

Deeper searches needed to remain responsive and could finish after the player had already started a new match.

How I solved it

Ran the search on a worker using a board snapshot, then returned the move to the JavaFX thread. A match revision token discards results from an earlier match.

What changed

The rule suite checks 7,560 positions across both variants. This supports move correctness.
