Inside the implementation

OOP behind the FPS

The Blueprint-to-C++ migration became a practical exercise in object-oriented design. I mapped each feature’s triggers, state and dependencies, then divided gameplay rules from editable assets and presentation. C++ owns input, weapons, health and waves; Blueprint subclasses supply assets and tuning, while StateTree retains the zombie’s Chase/Attack transitions.

  2. CommitAnimation notify transfers ammo
  3. PublishWeapon broadcasts OnAmmoChanged
  4. PresentCharacter forwards data to HUD

02 / Object-oriented principles in practice

Encapsulation

The firing timer, reload-commit flag and FireInternal() are private. Public operations check state before changing ammunition. BlueprintReadOnly blocks Blueprint writes, although ammunition fields remain public to C++.

Inheritance

Native weapon and zombie classes build on Unreal’s AActor and ACharacter. Blueprint subclasses reuse the rules while supplying meshes, animations and default values.

Polymorphism

AFPSRangeTarget implements IFPSBulletHitReceiver::ReceiveBulletHit(), so the weapon can report a hit without knowing the concrete target class. Player and zombie override TakeDamage() for their own responses.

Abstraction

StartFire() and Reload() expose an action request while hiding timer, trace and animation coordination. The hit-receiver interface defines the operation and leaves the response to the receiver.

03 / Make reload a guarded state transition

Reloading has three stages: request, ammunition commit and animation completion. The request checks eligibility and starts the montages. The authored notify commits the transfer; FinishReload returns the weapon to Ready when the arm montage ends. An interruption before the notify transfers nothing, while an interruption afterwards retains the committed ammunition.

CommitReload checks state and owner validity, rejects duplicate notifications, and transfers the smaller of free magazine space and available reserve. Broadcasting the result lets the character update the HUD without coupling the weapon to UI layout.

Inspect CommitReload()C++

Annotated source excerpt: Source/My_UE_FPS/Weapons/FPSWeaponBase.cpp · CommitReload().

void AFPSWeaponBase::CommitReload()
{
    // Ignore late or duplicate notifies, and invalid or dead owners.
    if (WeaponState != EFPSWeaponState::Reloading ||
        bReloadCommitted || !Player.IsValid() || Player->IsDead())
        return;

    // One animation-driven reload may transfer ammunition only once.
    bReloadCommitted = true;
    // Transfer only what fits in the magazine and exists in reserve.
    const int32 Transfer = FMath::Min(
        FMath::Max(0, MagazineSize - CurrentAmmo), ReserveAmmo);
    CurrentAmmo += Transfer;
    ReserveAmmo -= Transfer;

    // Listeners update presentation; the weapon does not access the HUD.
    OnAmmoChanged.Broadcast(CurrentAmmo, ReserveAmmo);
}

04 / Composition and lifecycle management

UFPSFootstepComponent keeps footstep behaviour separate from the character’s other responsibilities. TObjectPtr stores reflected asset references, while TWeakObjectPtr tracks objects without owning them. EndPlay clears timers and event subscriptions.

Each zombie has independent attack-instance data for elapsed time and its one-hit flag. Death stops AI and movement, broadcasts an event and enables ragdoll; the wave director counts the death immediately rather than waiting for corpse removal. This connects object lifecycle rules to correct wave progression.

05 / Reuse with explicit boundaries

Firearms with the same hitscan model can reuse AFPSWeaponBase with different damage, cadence and presentation settings. Zombie variants can reuse health and death handling while changing assets or StateTree parameters. A different firing model still needs code changes: FireInternal() is private and non-virtual.

The smoke scenario exercises firing, timer cleanup and the actual montage notify, checking ammunition conservation and return to Ready. Combat checks use two zombies to verify independent attack timing and that dead enemies cause no further damage.

Preserving the timing behind a reload.

The challenge

A reload crossed input, weapon state, animation notifications, ammunition transfer, and HUD updates. Translating individual graphs risked losing the assumptions connecting them.

How I solved it

Kept the animation notify responsible for ammunition transfer, separated request, commit, and completion, and replaced direct weapon-to-widget access with ammunition-change events.

What changed

The smoke scenario checks animation-triggered reloading and ammunition conservation.
